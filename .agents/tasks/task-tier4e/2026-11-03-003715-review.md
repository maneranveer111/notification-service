# Provider precedence fix, Docker packaging, landing page, OSS files

This task delivers five features against the notification-service: a backend fix to the provider-precedence logic so workspace-owned credentials always win over the platform fallback; a frontend runtime-config pattern (`absoluteApiBase()`) that lets the API base URL be injected at container startup without rebuilding the bundle; Docker packaging for both services plus a six-service `docker-compose.yml`; a public landing page and API docs page; and a full suite of OSS files (LICENSE, README, CONTRIBUTING, SECURITY, GitHub templates, CI docker job). All five FEATs are marked completed and the commit history confirms five sequential commits on the `tier-1` branch.

Watch for: (1) **confirmed** — `DocsPage.jsx` uses `"reason": "unsubscribe"` in both the curl example and the example response for the Suppressions section, but the backend schema only accepts `opt_out` and `bounce`; any visitor who copies this example will get a 422. (2) **confirmed** — `LandingPage.jsx` and `DocsPage.jsx` call `absoluteApiBase()` at module scope; if a deployer sets `API_BASE_URL` to a value different from the Vite build arg, the public pages will show stale curl examples while authenticated pages show the correct runtime URL. (3) **confirmed** — `backend/Dockerfile` has no `EXPOSE` instruction, making the intended port invisible in image metadata (no runtime impact).

**Verdict**: NEEDS_CHANGES

## High-level view

The provider-precedence logic in `providers.py` is correctly restructured: own active credentials checked first, platform fallback only if `use_platform_providers` is true or workspace is `None`, empty/`None` otherwise. All four functions (`resolve_email_providers`, `resolve_sms_provider`, `has_email_provider`, `has_sms_provider`) follow the same three-step pattern, and the eight new backend tests cover the logic exhaustively, including the suppression reason validation.

`absoluteApiBase()` is exported and used by all four pages. `OverviewPage` and `ApiKeysPage` call it inside the component function, picking up the runtime `window.__APP_CONFIG__` value on every render. `LandingPage` and `DocsPage` call it at module scope to populate string constants, which freezes the value at module initialisation time. In the standard Docker deployment (`API_BASE_URL` equals the build arg `/api`) this is harmless, but if a deployer sets a different `API_BASE_URL` at runtime the public-page curl examples will still show the build-time value while the authenticated pages show the correct one.

Docker packaging is complete and structurally sound. The backend Dockerfile is minimal with a non-root user and no CMD. The frontend is multi-stage (node:20-alpine builder → nginx:alpine). `nginx.conf` has SPA fallback, `/api/` proxy, `no-store` on `config.js`, static asset long-cache, and three security headers. `docker-compose.yml` has all six required services, uses `REDIS_URL` for both Celery broker and backend (not the legacy `CELERY_BROKER_URL`), and uses `service_completed_successfully` for the migrate dependency. One gap: `backend/Dockerfile` has no `EXPOSE` instruction, which is a minor documentation issue but not a runtime defect.

The `DocsPage` Suppressions section documents `"reason": "unsubscribe"` in both the curl example and the example response. The backend only accepts `opt_out` and `bounce` (enforced by `Literal["opt_out","bounce"]` on `SuppressionCreate`). Any consumer copying this example will get a 422. The schema field description also says `"e.g. unsubscribe, bounce"`, compounding the mismatch.

The OSS files are complete: LICENSE (MIT 2025), README with Mermaid diagram and Quickstart, `docs/self-hosting.md` with Prerequisites, `docs/deployment.md`, CONTRIBUTING with Running Tests, SECURITY with Reporting, GitHub templates, and a `docker` CI job. `scripts/generate_env.py` exists and uses `secrets` from stdlib only.

### DocsPage suppression reason mismatch

`DocsPage.jsx` lines 249, 257, 263 use `"unsubscribe"` as the documented and demonstrated suppression reason. `SuppressionCreate.reason` is `Literal["opt_out", "bounce"]` — `"unsubscribe"` is rejected with 422. The field description (`"e.g. unsubscribe, bounce"`) also lists a value that will not be accepted. This is a user-facing documentation bug: the docs page is the primary API reference for self-hosted deployments.

Fix: change the field description to `"opt_out or bounce"`, the curl example `reason` to `"opt_out"`, and the example response `reason` to `"opt_out"`.

### Module-level absoluteApiBase in public pages

```js
// LandingPage.jsx line 5 — module scope
const curlExample = `curl -X POST ${absoluteApiBase()}/notifications/email ...`;

// DocsPage.jsx line 5 — module scope
const apiBase = absoluteApiBase();
```

These freeze the base URL at module initialisation time. In a browser the `config.js` script tag fires before the module bundle, so `window.__APP_CONFIG__` is populated in time — the Docker entrypoint writes `config.js` into the served directory before nginx starts serving, so this works correctly in the standard Docker deployment. The issue is narrower: if a deployer sets `API_BASE_URL` to a value *different* from the Vite build arg `VITE_API_BASE_URL=/api`, the public pages will still show `/api`-rooted curl examples while the authenticated pages would show the correct runtime value. The inconsistency is confirmed by comparing with `OverviewPage` (line 109: `const apiBase = absoluteApiBase()` inside the component) and `ApiKeysPage` (line 198: same pattern inside the component).

### Backend Dockerfile missing EXPOSE

`backend/Dockerfile` correctly omits CMD (commands are per-service in compose). It also omits `EXPOSE 8000`. This has no runtime effect — the port binding in `docker-compose.yml` works regardless — but `EXPOSE` serves as documentation for `docker inspect` and tooling that reads image metadata. Low severity; spec did not require it, but noting it as a minor gap.
