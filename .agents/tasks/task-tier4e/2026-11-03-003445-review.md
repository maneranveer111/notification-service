# Tier 4E: provider precedence, runtime config, Docker packaging, landing/docs pages, OSS files

This task retrofits five independent concerns into an existing FastAPI + React notification service: fixes inverted provider-precedence logic in the backend, wires a runtime API base URL override into the frontend, adds a full Docker packaging layer, adds a landing page and API docs page, and creates the standard OSS open-source file set. All five feature branches landed on `tier-1` in five sequential commits, each self-contained. The change is broad (169 files, ~25k line net addition) but touches well-isolated concerns; the main integration point is `absoluteApiBase()` threaded from `api.js` through every page that constructs API URLs.

**Watch for:** Module-level calls to `absoluteApiBase()` in `DocsPage.jsx` and `LandingPage.jsx` freeze the API base in a constant — self-hosted deployments with a custom domain will see `http://localhost:8000` rendered in the docs UI (confirmed). The DocsPage suppression curl example uses `reason: "unsubscribe"` — a value the backend rejects with 422 (confirmed). FEAT-001 test coverage does not include `has_email_provider` / `has_sms_provider`, the gating functions called at notification-create time (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The provider-precedence rewrite in `providers.py` is correct. All four resolver functions (`resolve_email_providers`, `resolve_sms_provider`, `has_email_provider`, `has_sms_provider`) follow the same three-step rule: own active credentials first, platform fallback if `use_platform_providers` is True, empty/None otherwise. The 8-test suite covers the resolver functions directly and validates both accepted and rejected suppression reasons.

`absoluteApiBase()` is properly exported from `api.js` and reads `window.__APP_CONFIG__.API_BASE_URL` before the Vite env var. `OverviewPage` and `ApiKeysPage` call it inside their component functions, picking up the runtime-injected value. `DocsPage` and `LandingPage` call it at module scope and freeze the result in a constant. The Docker entrypoint override is present and correct, but these two pages display the frozen `http://localhost:8000` value in rendered UI regardless of what `config.js` contains.

The Docker layer is complete and correctly structured. `backend/Dockerfile` has no `CMD`; per-service commands are set in `docker-compose.yml`. The frontend is multi-stage; the entrypoint script writes `config.js` from `API_BASE_URL` at container start. The compose file uses `REDIS_URL` for both Celery broker and backend — consistent with `celery_app.py`. No legacy `CELERY_BROKER_URL` or `CELERY_RESULT_BACKEND` appears anywhere.

`LandingPage` and `DocsPage` exist, import `absoluteApiBase`, and the build passes. `HomeRoute` in `App.jsx` correctly routes unauthenticated visitors to `LandingPage`. The `/docs` route is public. Layout's `NAV` array includes Docs before Notifications, unrestricted. The DocsPage suppression section documents `reason: "unsubscribe"` — a value the backend schema rejects (only `opt_out` and `bounce` are valid).

All OSS files are present. The README has a Mermaid architecture diagram and a Quickstart section. The CI `docker` job validates the compose config and builds both images without starting any containers.

### Module-level `absoluteApiBase()` in DocsPage and LandingPage

`DocsPage.jsx` and `LandingPage.jsx` both call `absoluteApiBase()` at the module's top level:

```js
// DocsPage.jsx line 5
const apiBase = absoluteApiBase();

// LandingPage.jsx line 5
const curlExample = `curl -X POST ${absoluteApiBase()}/notifications/email ...`;
```

The result is frozen in a module-scope constant — once set, it never updates. This means the `apiBase` value rendered inline in DocsPage's intro paragraph ("Base URL: `http://localhost:8000`") and embedded in every curl example stays as `http://localhost:8000` for any self-hosted deployment with a custom domain, regardless of what the Docker entrypoint wrote into `config.js`. `OverviewPage` and `ApiKeysPage` call `absoluteApiBase()` inside their component functions, correctly reading the runtime value on each render. Moving DocsPage and LandingPage to the same pattern closes the inconsistency.

**Confidence: confirmed** — module-level assignments at line 5 of both files; `OverviewPage` line 109 and `ApiKeysPage` `HowToUseBox` line 198 show the correct inside-component pattern.

### DocsPage suppression example sends an invalid reason

The Suppressions section in `DocsPage.jsx` shows:

```json
{
  "recipient": "user@example.com",
  "channel": "email",
  "reason": "unsubscribe"
}
```

`SuppressionCreate` in `backend/app/schemas/notification.py` line 77 defines `reason: Literal["opt_out", "bounce"] = "opt_out"`. A user copying this example gets a 422 response. Change to `"reason": "opt_out"`.

**Confidence: confirmed** — cross-checked `DocsPage.jsx` SECTIONS array and schema line 77.

### `has_email_provider` / `has_sms_provider` coverage gap

`resolve_email_providers` and `resolve_sms_provider` are tested by tests 1–4 in `test_tier4e_backend.py`. The `has_email_provider` and `has_sms_provider` functions in `providers.py` follow the same three-step logic but are separate code paths. These functions are called in `notifications.py` at request time to gate whether a send request should be accepted at all — they're on the hot path for every send. The 8-test suite doesn't exercise them. Given that the precedence logic was recently inverted and then fixed, a test confirming the has_* functions return the correct boolean for own-creds and no-creds scenarios closes a real coverage gap.

**Confidence: confirmed** — no test in `test_tier4e_backend.py` calls `has_email_provider` or `has_sms_provider`.
