# Provider precedence fix, Docker packaging, landing/docs pages, OSS files

This is a second-pass review. The first pass (2026-11-03-003715-review.md) raised two blocking concerns: (1) `DocsPage.jsx` documented `"unsubscribe"` as a valid suppression reason when the backend only accepts `opt_out` and `bounce`; (2) `LandingPage` and `DocsPage` called `absoluteApiBase()` at module scope, freezing the URL at bundle initialisation time. Both were fixed in commit `658e46d`. This pass verifies those fixes and checks for any new concerns introduced by the fix commit.

Watch for: nothing blocking. Both prior findings are confirmed resolved. The fix commit also added 4 extra tests (tests 9–12) for `has_email_provider` / `has_sms_provider` beyond the 8 required.

**Verdict**: APPROVED

---

## High-level view

The `DocsPage` suppression section now uses `"reason": "opt_out"` in the curl example, the example response, and the field description reads `"opt_out or bounce"`. The mismatch is gone.

`LandingPage.jsx` moves `curlExample` construction inside the component function body (line 43), so `absoluteApiBase()` is called at render time and reads the live `window.__APP_CONFIG__` value. `DocsPage.jsx` calls `absoluteApiBase()` at the top of the `DocsPage` function body (line 273), before building the sections array. Both now match the pattern used by `OverviewPage` and `ApiKeysPage`.

The four new tests (9–12) cover `has_email_provider` and `has_sms_provider` with own-cred-returns-true and no-cred-no-platform-returns-false cases. These directly exercise the two helper functions whose precedence logic was also fixed in FEAT-001, closing a coverage gap that existed after the initial 8 tests.

No new concerns were introduced by the fix commit. The three files changed (`DocsPage.jsx`, `LandingPage.jsx`, `test_tier4e_backend.py`) are narrow, targeted fixes with no side effects on other components.
